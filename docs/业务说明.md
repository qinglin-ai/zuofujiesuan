### 二、功能需求清单

#### A. 用户与账号（worker + admin）

| 编号 | 需求 | 说明 |
|------|------|------|
| A1 | 微信登录 | code → openid → 云函数鉴权，身份识别以 `_openid` 为准 |
| A2 | 实名注册 | 用户在「用户」页手动填写手机号 + 真实姓名（昵称、头像可选），提交后状态为「待审批」；已审批通过后不可自行修改 |
| A3 | 注册审批 | admin 审批通过/驳回，通过后方可接单 |
| A4 | 账号资格管理 | admin 可封禁/解封（独立于审批） |
| A5 | 收款账户绑定 | 在「用户」页绑定银行卡（开户行、卡号、持卡人姓名），**卡号须为 16~19 位数字**（借记卡多为 16/17/19 位、信用卡 16 位），提现前必须先绑定，未绑定不可提现；展示时卡号仅显示尾 4 位，持卡人姓名与真实姓名按脱敏口径展示 |
| A6 | 后台账号鉴权 | H5 后台 admin 登录与角色校验 |

#### B. 能力认证与考试（人工审批判定）

| 编号 | 需求 | 说明 |
|------|------|------|
| B1 | 人工准入评定 | 考试判定由 admin 人工审批（examPassed），绑定「任务 × 标注类型」 |
| B2 | 能力等级评定 | admin 评定 junior / middle / senior 等级 |
| B3 | 质量指标维护 | 维护该任务该类型的质检通过率（passRate） |

#### C. 任务与作业（核心链路）

| 编号 | 需求 | 说明 |
|------|------|------|
| C1 | 任务创建 | admin 设置：任务名、任务描述、标注类型、quantity、unitPrice、难度、requireLevel、totalPeople、deadline、forbiddenItems、样例 |
| C2 | 任务浏览 | worker 按开启状态/标注类型浏览可用任务 |
| C3 | 任务领取 | 校验通过后领取，**并发防超领**（事务 + 唯一索引 + 条件自增）；满足条件即分配 |
| C4 | 作业提交 | worker 在外部任务系统完成作业后，本系统将 assignment 置为 submitted |
| C5 | 外部核验回写 | admin 在外部系统核验后回写结果（pass/reject）至本系统 |
| C6 | 任务关闭 | 到期或 admin 手动关闭，未领取名额失效，已领取继续核验 |

#### D. 资金链路（最敏感）

| 编号 | 需求 | 说明 |
|------|------|------|
| D1 | 佣金结算 | 核验通过即入账，金额 = 提交数量 × 单价 unitPrice，**幂等防重复**（assignmentId 唯一索引） |
| D2 | 余额管理 | 可提现余额原子增减，流水与余额一致（事务） |
| D3 | 提现申请 | 校验余额充足且已绑卡，内免二次审核，扣减余额写 pending 记录 |
| D4 | 提现回写 | 到账后置为 paid（微信支付）。
| D4-1 | 自动回写 | 对接微信支付回调/轮询自动置 paid |
| D4-2 | 半自动回写 | 财务在后台「确认到账」置 paid（作为自动不可用的兜底） |
| D5 | 台账/对账导出 | 按日聚合佣金流水 + 提现记录导出报表，可追溯 |
| D6 | 微信支付开通 | 微信支付能力本期接入（预留企业打款能力） |

#### E. 辅助功能

| 编号 | 需求 | 说明 |
|------|------|------|
| E1 | 违规与黑名单 | admin 记录处罚（警告/停派/封禁），用于评估与禁入 |
| E2 | 公告管理 | 公告/流程/项目动态/FAQ，admin 发布，worker 查看 |

### 二、状态机定义（冻结）

#### 2.1 任务状态（tasks.status）—— 任务自身生命周期

```
open ──满员/开工──▶ inProgress
open/inProgress ──到期或手动──▶ closed（终态）
closed：未领取名额失效，已领取作业继续按核验流程结算
```

| 状态 | 含义 | 触发 |
|------|------|------|
| open | 可领取 | 创建后初始态 |
| inProgress | 进行中（满员开工） | claimedCount 达 totalPeople |
| closed | 已关闭 | 到达 deadline 或 admin 手动关闭 |

#### 2.2 作业状态（assignments.status）—— 单个作业进度（一人一任务一条）

```
claimed ──提交──▶ submitted ──核验──▶ passed（→ 触发结算）
                              └──▶ rejected（不结算）
```

| 状态 | 含义 | 触发 |
|------|------|------|
| claimed | 已领取 | 领取成功 |
| submitted | 已提交 | worker 在外界作业完成并提交 |
| passed | 已通过 | 外部核验通过回写 |
| rejected | 未通过 | 外部核验未通过回写 |

#### 2.3 提现状态（withdrawals.status）

```
pending ──微信转账成功回调──▶ paid
pending ──转账终态失败/余额不足──▶ rejected
```

| 状态 | 含义 | 触发 |
|------|------|------|
| pending | 提现中（含「待收款确认/转账中」微信侧中间态） | 用户申请成功、余额扣减后 |
| paid | 已到账 | 微信转账 SUCCESS 回调 / admin 半自动确认对账 |
| rejected | 已拒绝 | 校验失败（余额不足等）或转账终态 FAIL（达重试上限） |

> 微信侧单据状态镜像 `transfer_status`（ACCEPTED / PROCESSING / WAIT_USER_CONFIRM / TRANSFERING / SUCCESS / FAIL / CANCELING / CANCELLED）同步落库，`status=pending` 期间可据此细分展示「待收款确认/转账中」。

#### 2.4 用户状态（users 双字段分离）

- `approvalStatus`（注册准入）：pending → approved / rejected
- `status`（账号资格）：active / blocked

> 资格状态与作业进度完全分离，支撑一人多任务独立流转。

### 三、主链路逐步详解

#### S1 创建（admin）
- 输入：任务名、任务描述、标注类型、quantity、unitPrice、难度、requireLevel、totalPeople、deadline、forbiddenItems、样例
- 落库：tasks(status=open, claimedCount=0)
- 异常：无（admin 权限校验）

#### S2 领取（worker）
- 前置校验（缺一不可）：审批通过 `approvalStatus=approved`、账号正常 `status=active`、考试准入通过、能力等级满足 requireLevel、未领取过该任务、未满员 `claimedCount<totalPeople`
- **并发控制（⚠关键）**：云函数事务内读取 claimedCount → 判断未满员 → 原子 +1 → 插入 assignment
- 兜底：assignment 复合唯一索引 `(_openid, taskId)`
- 满员：同事务内将 tasks.status 置 inProgress
- 异常分支：见第四章

#### S3 提交（worker，作业在外部系统）
- 外部系统完成作业 → 本系统 assignment 置 submitted，记 submitTime
- 异常：未领取不可提交（状态机校验）

#### S4 外部核验回写（admin）
- admin 到外部系统核验 → 回写本系统 pass/reject
- 落库：assignment → passed/rejected + quality_checks（result、externalRefNo、remark、checkTime、checkedBy）
- **通过才触发结算**

#### S5 结算（核验通过自动触发，⚠关键）
- 佣金金额 = 提交数量 × unitPrice；`commissions.assignmentId` 唯一索引保证幂等
- 事务：插佣金流水 + balances.availableBalance += 金额，任一失败回滚
- 记 assignment.finishTime

#### S6 提现（worker）与回写
- 申请：校验 `amount ≤ availableBalance` 且已绑卡 → 事务内 balances -= amount + 写 withdrawals(pending)（HTTP 调用不放事务内）
- 到账（自动为主，T4-6）：提交后同步调用微信「商家转账到零钱」创建转账单；用户须在微信「微信支付」转账消息中**点击「确认收款」**（微信转账规则，非本系统内操作），期间转账单 `transfer_status=WAIT_USER_CONFIRM`、提现单保持 pending（小程序展示「待收款确认」引导去微信确认）；异步回调 SUCCESS → 置 paid；**防重铁律**——创建遇 `ALREADY_EXISTS`/`SYSTEM_ERROR`/`FREQUENCY_LIMIT_*`/网络异常等结果未知错误时**先查单**，仅当查单明确 FAIL 才生成新 `out_bill_no` 换单重试（上限 1 次），绝不盲目换单防重复打款
- 到账（半自动兜底）：未启用自动打款（`WXPAY_ENABLED=0`）或自动流程异常时，保留 pending，由财务「确认到账」置 paid
- 失败：校验不通过或转账终态 FAIL 达重试上限 → 置 rejected + 记录 fail_reason，**余额不自动退回**，由管理员「失败补发」重新打款
- **CANCELLED（用户超时未确认，转账被微信取消、钱退回商户账户）**：确定性终态，安全生成新 `out_bill_no` 换单重试一次；重试耗尽仍 CANCELLED → 置 rejected + fail_reason，且**金额退回用户可提现余额**（`balance_refunded=1`，可重新申请提现），已退回单禁止管理员「失败补发」（防重复打款）
- 提现免 admin 二次审核；未绑定收款账户不可提现

#### S7 关闭
- deadline 到达或 admin 手动关闭 → tasks.status=closed
- 未领取名额失效；已提交待核验作业继续走 S4~S5 结算

### 四、异常分支与约束（冻结）

| 编号 | 场景 | 处理 | 归属状态机 |
|------|------|------|-----------|
| E1 | 并发同时领取同一任务最后名额 | 事务条件自增，who claimedCount<totalPeople，仅一方成功，其余返回「任务已满员」 | S2 |
| E2 | 同一人重复领取同一任务 | 复合唯一索引 `(_openid, taskId)` 拒绝 | S2 |
| E3 | 未满员但已关闭的任务 | 无 S2 领取入口（closed 不可领） | S2/S7 |
| E4 | 核验重复回写 | 以 assignmentId 幂等（单条）+ quality_checks 唯一索引防重 | S4 |
| E5 | 结算重复触发 | commissions.assignmentId 唯一索引幂等 | S5 |
| E6 | 提现余额不足 | 校验失败 → withdrawals=rejected，不扣金额 | S6 |
| E7 | 提现到账回写失败 | 自动打款异常（网络/超时结果未知）→ 保留 pending 防重复打款，回调或查单兜底 / admin 半自动确认到账兜底 | S6 |
| E8 | 关闭后再被核验 | 已领取作业继续核验结算，不受 closed 影响 | S4/S7 |
| E9 | 考试未通过仍领取 | S2 前置校验拦截（examPassed=false） | S2 |
| E10 | 自动打款创建单遇 ALREADY_EXISTS 等结果未知错误 | **先查单**：查单 SUCCESS → 直接置 paid；明确 FAIL → 生成新 out_bill_no 换单重试（≤1 次）；其余状态 → 保持 pending 等回调；绝不盲目换单（防重复转账资金风险） | S6 |
| E11 | 微信回调幂等 / 陈旧回调 | 回调按 out_bill_no 定位；已终态忽略；`event.out_bill_no` 与当前 `out_bill_no` 不一致（已换单）的迟到回调忽略 | S6 |

## 三、业务逻辑说明


> 本文件仅描述**业务流程与规则**，不包含数据库结构（库结构见《数据库结构说明.md》）。
> 技术底座：微信云开发（CloudBase）。涉及资金与并发安全的逻辑必须通过云函数执行，并配合数据库事务 / 唯一索引兜底。

---

### 一、角色定位

| 角色 | 职责 |
|------|------|
| worker（兼职人员） | 浏览/领取任务、提交作业、查看数据与佣金、申请提现、参加考试 |
| admin（管理员兼财务） | 注册审批、任务创建/分配、外部核验、能力评级、台账对账导出、违规处罚 |

---

### 二、任务完整生命周期

一个任务从创建到结算的全过程：

**① 创建（管理员）**
- 管理员创建任务，设置：任务名、标注类型、单人任务量（quantity）、单价（unitPrice）、难度、领取所需最低等级（requireLevel）、总人数（totalPeople）、截止时间（deadline）、禁用项（forbiddenItems）
- 初始状态：任务 `status = open`，已领取人数 `claimedCount = 0`

**② 领取（用户 worker）**
- 依次校验通过才允许领取：
  - 用户已通过注册审批（`approvalStatus == approved`）且账号正常（`status == active`，未封禁）
  - 任务处于开启状态（`status == open`，未关闭）
  - 能力达标：已通过该任务该标注类型的准入考试，且能力等级满足任务的 `requireLevel`（最低等级要求）
  - 当前未领取过该任务（同一人同一任务仅一条 assignment）
  - 未满员：`claimedCount < totalPeople`
- 领取动作必须在**事务 / 原子操作**内完成：原子更新 `claimedCount += 1`，失败则说明已满员，拒绝领取（详见"并发超领控制"）
- 领取成功生成一条 assignment（状态 `claimed`）；当 `claimedCount == totalPeople` 时任务可置为 `inProgress`（满员开工）

**③ 提交（用户 worker）**
- 用户在**外部专门任务系统**完成作业并提交
- 本系统更新 assignment 状态为 `submitted`，记录 `submitTime`

**④ 核验（管理员，外部系统）**
- 管理员到外部系统核验该作业通过与否，仅将结果回写本系统：
  - 通过 → assignment 置为 `passed`，记录核验人、核验时间
  - 未通过 → assignment 置为 `rejected`，记录核验人、核验时间
- 同步写入一条**外部核验结果记录**（结果、外部核验单号、备注、核验时间）用于留痕追溯

**⑤ 结算（核验通过触发）**
- 核验通过后触发佣金入账（详见"佣金入账幂等"）
- **佣金金额 = 提交数量 × 单价 unitPrice**（提交数量由兼职人员提交作业时**前端上报**，后端据此计算本次周期佣金；`commissions.amount` 已含数量信息，可由 amount ÷ unitPrice 反算核对，无需单独存数量字段）
- assignment 记录最终完成时间

**⑥ 关闭（管理员/系统）**
- 到达 `deadline` 或管理员手动关闭任务
- 未领取名额自然失效；已领取待核验的作业继续完成核验

### 三、并发超领控制（防"不限量人数领取"）

- **领取入口必须且只能通过云函数处理**，禁止客户端直接修改任务的 `claimedCount`
- 核心逻辑（CloudBase 事务）：
  1. 事务内读取任务当前 `claimedCount`
  2. 判断 `claimedCount < totalPeople`，不满足则回滚，返回"任务已满员"
  3. 满足则执行原子 `claimedCount += 1`，并插入 assignment
- 兜底机制（双保险）：
  - **唯一索引**：assignment 的复合唯一索引 `(_openid, taskId)`，即使事务边界漏网，数据库约束也会拒绝同一人重复领取
  - **条件原子更新**：使用 `where claimedCount < totalPeople` 下的条件自增，确保并发下不会超领

---

### 四、佣金入账幂等（防重复结算）

- 一个任务（assignment）核验通过后，**只能产生一条**佣金流水
- 兜底机制：佣金流水按来源作业 `assignmentId` 建立唯一索引
  - 入账前先查该 `assignmentId` 是否已有佣金，有则直接返回（幂等）
  - 即使并发重复触发，唯一索引也会让第二条插入失败
- 入账流程在**事务内**完成：插入佣金流水 + 更新用户佣金账户余额，任一失败整体回滚，保证"流水与余额一致"

---

### 五、资金流转（核心资金链路）

1. 用户完成作业并提交 → 进入核验队列
2. 管理员到外部系统核验通过 → 更新 assignment 为 `passed`，记录外部核验结果
3. 触发佣金：生成佣金流水（记录到日）→ 同步更新用户可提现余额（事务原子操作）
4. 核验未通过 → 更新 assignment 为 `rejected`，记录外部核验结果，不产生佣金
5. 用户申请提现：校验 `amount ≤ availableBalance`，成功则扣减余额并写入提现记录（pending → paid），**无需管理人员二次审核**；默认走微信「商家转账到零钱」自动打款，未启用时回退半自动人工确认
6. 财务 / 管理员的"台账 / 对账导出"：基于佣金流水（按入账日期日粒度）与提现记录生成报表，对账可追溯

---

### 六、提现回写流程（T4-6 自动打款）

- 提现**免管理人员二次审核**，但**到账必须闭环回写**，否则"已提金额"与账户状态无法闭环：
  1. 用户发起提现：校验 `amount ≤ 可提现余额`、已绑定收款账户（**绑卡前须先取得用户对《用户服务协议》《隐私政策》的授权同意**）且未超每日提现申请次数上限（`WITHDRAW_DAILY_MAX`，默认 1 次/日）
  2. 事务内：扣减可提现余额并写入提现记录（`status = pending`，记录申请时间、账户快照）——**HTTP 调用不放事务内**，避免持锁
  3. 支付侧处理完成后回写提现记录为 `paid` 并记录到账时间

    触发方式二选一：
    - **自动（默认，T4-6）**：提交后同步调用微信「商家转账到零钱」（APIv3）创建转账单，微信异步回调/查单回写
    - **半自动（兜底）**：`WXPAY_ENABLED=0`（未配置真实商户凭据）或自动流程异常时，财务在管理后台对 pending 状态执行"确认到账"，置为 paid
  4. 校验失败（余额不足）时直接置为 `rejected`，不扣金额

**提现规则（小程序提现页公示口径，与后端校验一致）**：

| 规则项 | 口径 | 后端实现 |
|--------|------|----------|
| 可提现额度 | 以当前可提现余额为上限；单笔金额需 > 0 且 ≤ 可提现余额 | `apply_withdrawal` 余额校验 |
| 每日提现次数 | 每日（北京时间自然日）最多 `WITHDRAW_DAILY_MAX` 次（默认 1）；含当日已提交的全部申请（含已失败/已取消的单），超限返回 400 | `_today_withdraw_count` + `withdraw_rule_view` |
| 提现时间 | 7×24 小时均可提交提现申请 | 无时间窗限制 |
| 到账时间 | 经微信「商家转账到零钱」发放；用户在微信「微信支付」转账消息点击「确认收款」后实时到账微信零钱；超时未确认自动取消并退回可提现余额 | T4-6 自动打款 + 回调收口 |
| 手续费 | 不收取手续费 | 提现额 = 扣减余额 |

> 规则通过 `GET /api/wallet/me` 的 `withdraw_rule`（`daily_limit` / `today_used` / `today_remaining`）返回，小程序「我的资金」页「提现规则」卡片展示（微信审核要求：提现页须清晰展示提现规则）。

**防重复打款铁律（资金安全核心）**：
- 创建转账单遇 `ALREADY_EXISTS` / `SYSTEM_ERROR` / `FREQUENCY_LIMIT_EXCEED` / `RATELIMIT_EXCEEDED` / `FREQUENCY_LIMIT` / 网络异常（结果未知）时，**必须先查单**（按 out_bill_no），**绝不立即换单重试**
- 查单结果：SUCCESS → 直接置 paid；明确 FAIL → 生成**新 out_bill_no** 换单重试（默认上限 1 次，`WXPAY_RETRY_MAX`）；其余非终态 → 保持 pending 等回调
- 确定性错误（`PARAM_ERROR` / `INVALID_REQUEST` / `NO_AUTH` / `SIGN_ERROR` / `NOT_ENOUGH`）换单必败 → 直接置 rejected + 记录 fail_reason，**余额不自动退回**，由管理员「失败补发」（`POST /api/wallet/withdrawals/<id>/retry`）重新打款
- **用户确认模式（WAIT_USER_CONFIRM）**：商家转账遵循微信「用户确认收款」规则——转账发起后可能进入 `WAIT_USER_CONFIRM`，**用户需在微信「微信支付」转账消息中点击"确认收款"**（不在本系统内操作）后转账才完成；期间提现单保持 pending（小程序显示"待收款确认"并提示去微信确认）
- **CANCELLED（超时未确认被微信取消，钱退回商户账户）**：属确定性终态，安全生成**新 out_bill_no** 换单重试一次；重试耗尽仍 CANCELLED → 置 rejected、记录 fail_reason，并把金额**退回用户可提现余额**（`balance_refunded=1`），用户可重新申请提现；已退回单禁止管理员「失败补发」（防重复打款）
- 回调幂等：`out_bill_no` 定位记录，已终态忽略；与当前单号不一致的陈旧回调忽略
- 单号生成：`WD{提现id}A{尝试次数}`（纯数字字母、商户内唯一、随换单递增）

### 七、辅助流程

#### 7.1 注册与准入
- 新用户注册 → 状态为"待审批"
- 管理员审批通过后才能接单；审批驳回则无法使用接单功能
- 账号封禁（冻结）独立于审批，封禁期间无法领取 / 提交任务

#### 7.2 能力认证与考试
- 用户领取某类标注任务前，需通过该任务该类型的准入考试
- 认证记录绑定具体任务与标注类型，考核通过后方可领取对应类型任务
- **领取资格口径**：需存在对应认证记录且 `exam_passed` 为真、`level` 非空、且 `level` ≥ 任务 `require_level`（等级从低到高：junior < middle < senior）
- **兼职端**：小程序「用户」页与任务详情页「去认证」入口进入能力认证页（`pages/certify`），可查看本人认证记录、发起认证（提交考试成绩 0~100，`POST /api/certifications`，默认 ≥60 视为通过）
- **管理端**：管理后台「能力认证」页可对已有认证记录评级（`POST /api/certifications/<id>/rate`），并可**指派/覆盖认证**（`POST /api/certifications/grant`，按 openid+任务+标注类型从零授予或覆盖，写 level/exam_passed/pass_rate/reviewed_by）

#### 7.3 违规与处罚
- 管理员可对提交无关内容、改动原图等违规行为记录处罚（警告 / 停派 / 封禁）
- 处罚记录用于人员评估与黑名单管理
