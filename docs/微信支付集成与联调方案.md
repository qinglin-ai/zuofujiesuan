## 一、微信支付「商家转账到零钱」自动打款集成方案


> 文档版本：2026-09-03 ｜ 依据微信官方文档 2025.03.21《商家转账用户确认模式-发起转账》接口
> 关联：后端提现流程（backend/app/api/wallet.py）、Withdrawal 模型（backend/app/models.py）

### Context（背景与目标）

本系统（Flask 兼职管理 + 微信小程序）目前提现流程为：兼职申请提现 → 扣余额写 `withdrawals(status=pending)` → 财务在管理后台手动确认到账（半自动）。

目标：接入微信官方「商家转账到零钱」APIv3，实现**提现申请即全自动打款**，并已确认三项决策：

1. **触发方式**：兼职提交提现后，后端同步调用微信转账 API 自动打款，无需管理员干预。
2. **失败处理**：转账最终失败(FAIL)时**自动换单重试一次**（严格遵循官方防重铁律：遇 `ALREADY_EXISTS`/`FREQUENCY_LIMIT_*`/`SYSTEM_ERROR` 等必须先查单，查单明确 FAIL 才允许生成新 `out_bill_no` 重试；绝不立即换单，防止重复转账资金风险）。重试仍失败 → 状态置 rejected、记录 fail_reason、**余额不自动退回**，由管理员「补发」处理。
3. **小程序端**：同步更新「我的资金 / 提现记录」状态展示（转账中 / 待收款确认 / 已到账 / 已拒绝+原因）。

技术约束：Python 实现，不引入第三方微信支付 SDK，复用现有 `requests` + `cryptography`（43.0.3，已支持 RSA-OAEP(SHA-1)、AES-256-GCM、SHA256 签名）。

### 架构分层

- **`backend/app/wxpay/` 纯协议层**：不 import models/db，只负责 APIv3 签名、加解密、HTTP 请求、payload 构建、错误码分类。可脱离 Flask/DB 验证。
- **`backend/app/api/wallet.py` 业务编排层**：持有 Withdrawal 状态机，负责「何时发起、查单后是否换单重试、状态落库」等业务策略（复用现有 `login_required`/`require_role`/`_withdrawal_view` 风格）。

理由：防重/换单是**业务策略**（重试上限、余额不退、转人工），错误码含义是**协议事实**，两层职责清晰、可独立验证。

### 关键实现细节

#### 1. wxpay 协议层

- **请求签名**：`message = f"{method}\n{url_path}\n{timestamp}\n{nonce}\n{body}\n"`，商户 API 私钥 SHA256withRSA 签名后 base64；`Authorization: WECHATPAY2-SHA256-RSA2048 mchid="..",nonce_str="..",signature="..",timestamp="..",serial_no=".."`。
- **敏感字段**：`user_name` 用微信支付公钥 RSA-OAEP(**SHA-1**) 加密 + base64；请求头带 `Wechatpay-Serial = 微信支付公钥ID`。
- **回调验签**：`message = f"{timestamp}\n{nonce}\n{body}\n"`，微信支付公钥验 `Wechatpay-Signature`；比对 `Wechatpay-Serial` 与配置的公钥 ID 防公钥轮换攻击。
- **回调解密**：`resource{nonce, ciphertext, associated_data}` 用 32 位 APIv3 key AES-256-GCM 解密。
- **防重决策表** `classify_create_error(code)`：
  - `QUERY_FIRST`（结果未知，先查单）：`ALREADY_EXISTS` / `SYSTEM_ERROR` / `FREQUENCY_LIMIT_EXCEED` / `FREQUENCY_LIMIT` / `RATELIMIT_EXCEEDED` / 网络异常(Timeout/ConnectionError)。
  - `FINAL_FAIL`（确定性失败，换单必败，直接转人工）：`PARAM_ERROR` / `INVALID_REQUEST` / `NO_AUTH` / `SIGN_ERROR` / `NOT_ENOUGH` 等。
  - **只有 `QUERY_FIRST` 且查单结果明确 `FAIL` 才允许换单重试**，否则绝不生成新 `out_bill_no`。

#### 2. 数据模型与迁移

Withdrawal 新增列（与 003 一致）：
| 列 | 类型 | 说明 |

#### 3. 提现申请自动打款流程（wallet.py）

```
apply_withdrawal:
  1. 校验 amount>0、已绑卡、余额充足（不变）
  2. 事务内扣 available_balance + 写 Withdrawal(status=pending)；commit
     （HTTP 调用绝不放事务内，避免持锁；先落库拿 id）
  3. 提交后同步调用 auto_transfer_withdrawal(record)
  4. 返回 {"code":0, "data":_withdrawal_view(record)}

auto_transfer_withdrawal(w):
  client = wxpay.get_client(current_app)
  if client is None: return  # 未启用 → 保持 pending，沿用 manual 兜底
  while w.retry_count <= WXPAY_RETRY_MAX:
    out_bill_no = _gen_out_bill_no(w.id, w.retry_count)   # f"WD{id}A{attempt}" 纯数字字母
    try:
      resp = client.create_transfer_bill(build_transfer_payload(...))
    except WxpayError as e:
      if classify_create_error(e.code) == 'QUERY_FIRST':
        q = client.query_transfer_bill(out_bill_no)       # 先查单，绝不直接换单
        state = normalize_query(q)
        SUCCESS → _mark_paid; FAIL/CANCELLED → retry_count<MAX 则重试 else 终态收口; 其余 → _keep_pending
      else:  # FINAL_FAIL
        _mark_rejected(w, e)                               # 换单必败，转人工，余额不退
    except (Timeout, ConnectionError):
      _keep_pending(w)                                     # 结果未知，防重复打款
    state = normalize_create(resp)  # 2xx
    SUCCESS → _mark_paid; FAIL/CANCELLED → 重试/终态收口; 其余 → _keep_pending

  终态收口（FAIL vs CANCELLED 差异）：
  - FAIL 重试耗尽 → _mark_rejected（余额不退，管理员「失败补发」）
  - CANCELLED 重试耗尽 → _mark_rejected_refund（置 rejected + 金额退回用户可提现余额 + balance_refunded=1，
    禁止后续「失败补发」，用户重新申请提现即可）
  - 非终态（ACCEPTED/PROCESSING/WAIT_USER_CONFIRM/TRANSFERING/CANCELING）→ _keep_pending 等回调
```

私有辅助（均在 wallet.py）：
- `_gen_out_bill_no(id, attempt)`：纯数字字母、商户内唯一、随 attempt 递增保证每次换单都是新号。
- `_mark_paid`：`status=paid, paid_source=auto, pay_ref_no=out_bill_no, transfer_bill_no, transfer_status=SUCCESS, transfer_time=paid_time=now`。
- `_keep_pending`：只更新 `out_bill_no/transfer_bill_no/transfer_status`，status 保持 pending（前端显示「转账中」）。
- `_mark_rejected`：`status=rejected, transfer_status=FAIL, fail_reason=...`；**不回滚余额**（管理员补发处理）。

`handle_transfer_event(out_bill_no, event)`（notify 共用同一套收口，幂等）：
- 按 `out_bill_no` 查记录；查不到或 `event.out_bill_no != w.out_bill_no`（陈旧回调）→ 忽略。
- SUCCESS → `_mark_paid`；FAIL → 未达上限则换单重试一次，否则 `_mark_rejected`；其余 → `_keep_pending`。

#### 4. 回调 notify 端点

`POST /api/pay/transfer/notify`（无登录鉴权，微信签名保护）：
1. `request.get_data()` 原文 → `client.verify_notify(headers, raw_body)`，失败返回 `{"code":"FAIL","message":"验签失败"}` + 非 200（微信会重试）。
2. 解密 resource → 事件 dict（out_bill_no / transfer_bill_no / state / fail_reason / success_time）。
3. 幂等 + 陈旧忽略（见 `handle_transfer_event`）；查不到记录 → WARN 日志 + 返回 200 SUCCESS（停止微信无限重推）。
4. 返回 `200 {"code":"SUCCESS"}`。

#### 5. 管理后台

- `POST /api/wallet/withdrawals/<id>/retry`（`require_role("admin")`）「失败补发」：仅允许 rejected/FAIL（或 pending 但无 out_bill_no 的历史残留单）；**`balance_refunded=1` 的已退回单禁止补发**（防重复打款，提示用户重新申请）；**若已有 out_bill_no 先查单**，若旧单已 SUCCESS 则直接置 paid（防重复打款），否则清空转账字段、`retry_count=0`，重新调 `auto_transfer_withdrawal`；不重复扣余额。
- 既有 `POST .../confirm` 保留（manual 兜底）。
- `app.js`：提现列表新增「转账状态」列（FAIL 红色 + fail_reason）；pending 行保留「确认到账」；rejected 行加「失败补发」按钮 `doRetryPaid(id)`。

#### 6. 小程序 wallet 页

- `wallet.js`：`WD_STATUS = { pending: '转账中', paid: '已到账', rejected: '已拒绝' }`；`transfer_status==='WAIT_USER_CONFIRM'` 时显示「待收款确认」并提示**去微信「微信支付」转账消息点击确认收款**（确认不在本小程序内操作）；`rejected && balance_refunded` 时显示「已取消（余额已退回）」，并提示可重新申请提现；透传 `transfer_status / fail_reason / balance_refunded`。
- `wallet.wxml`：rejected 项补 `失败原因：{{item.fail_reason}}`；`onWithdraw` 成功提示改「提现已受理，转账中」。

- `docker-compose.yml` backend 段透传上述环境变量 + `- ./backend/certs:/app/certs:ro`；`.gitignore` 忽略 `backend/certs/*`。

### 验证 / 自测（无真实商户凭据）

1. **`flask wxpay-selfcheck`**（新增 CLI，零依赖零凭据）：内存生成临时 RSA 密钥对，断言签名回环、OAEP-SHA1 加解密一致、AES-GCM 回解、`classify_create_error` 决策表（ALREADY_EXISTS→QUERY_FIRST、PARAM_ERROR→FINAL_FAIL 等）。
2. **`WXPAY_MOCK=1` 全链路冒烟**：mock 客户端 create 返回 ACCEPTED / query 返回 SUCCESS，本地 MySQL 走完「扣余额→写记录→发起→状态回写」；curl POST `/api/pay/transfer/notify`（mock 跳过验签）触发 SUCCESS/FAIL，断言 DB 状态迁移 + 陈旧回调（伪造旧 out_bill_no）被忽略。
3. **防重单测（核心安全项）**：构造 `ALREADY_EXISTS` → 断言先查单、查单 FAIL 才换 `out_bill_no`（retry_count 0→1）、查单 SUCCESS 直接置 paid 不换单；确定性错误直接 rejected 不换单；构造 `CANCELLED` 回调 → 断言先换单重试（新 out_bill_no）、重试耗尽再 `CANCELLED` 置 rejected + 余额退回 + `balance_refunded=1`、重复 CANCELLED 回调幂等不重复退款、对已退回单 `retry` 返回 400 拒绝补发。
4. **真实凭据阶段**：`WXPAY_ENABLED=1` + 真实证书，内网穿透暴露 notify URL，发起小额真实转账，核对回调落库与小程序状态展示。

### 风险与注意

- 同步调用延迟：HTTP 调用不放 DB 事务内；`requests.timeout=10`；失败落 `_keep_pending` 转人工对账，绝不盲目换单（防重复打款最高优先级）。
- 存量 `pending` 无 `out_bill_no` 的历史记录：`retry` 接口可对其补发起。
- **用户确认模式**：转账可能进入 `WAIT_USER_CONFIRM` 等待用户在微信侧确认收款；超时未确认被取消（`CANCELLED`）后系统自动换单重试一次，仍取消则退回余额，避免资金无限挂起。
- 老数据卷不回放迁移：003/004 必须手动执行，且 `models.py` 同步加列，防止 schema 脱节。
- `WXPAY_ENABLED=0` 时行为完全回退到现有半自动流程，无破坏性。

## 二、微信支付「商家转账到零钱」实机联调测试方案


> 文档版本：2026-09-10 ｜ 适用：商户凭据已备齐，首次启用 `WXPAY_ENABLED=1` 前的实机联调
> 关联：本文第一部分（集成方案）、《业务说明.md》《数据库结构说明.md》

### 一、背景与目标

商户凭据（商户号、APIV3 密钥、商户 API 证书、微信支付公钥与公钥 ID）已准备完成。本方案定义从**凭据落位 → 配置核对 → 协议自检 → 真实小额转账 → 回调/异常分支 → 端到端验收**的全流程测试步骤与验收标准，用于确认自动打款可安全上线（核心约束：**防重复打款**，绝不盲目换单）。

### 二、凭据 → 配置项映射

| 已准备材料 | 用途 | 对应配置项（.env） | 状态 |
|---|---|---|---|
| 商户号 | 请求签名 mchid | `WX_MCHID` | 待填 |
| APIV3 密钥（32位） | 回调 AES-GCM 解密 | `WXPAY_API_V3_KEY` | 待填 |
| 商户 API 证书 zip | 解压得到 `apiclient_key.pem`（APIv3 仅用私钥） | `WXPAY_MCH_PRIVATE_KEY_PATH=certs/apiclient_key.pem` | 待落位 |
| 商户 API 证书登录密码 | **仅解压 zip 时使用**，程序不需要 | —（不入配置） | 已具备 |
| 微信支付公钥 | 姓名加密 / 回调验签 | `WXPAY_PLATFORM_PUBLIC_KEY_PATH=certs/pub_key.pem` | 已落位（`backend/certs/pub_key.pem`） |
| 微信支付公钥 ID | `Wechatpay-Serial` 头 + 验签比对 | `WXPAY_PLATFORM_PUBLIC_KEY_ID` | 待填 |

> **重要**：`crypto.py` 加载私钥 `password=None`，即 APIv3 使用未加密的 PEM 私钥；「证书登录密码」仅用于解压官方证书包，不写入任何配置。

#### 仍需准备/确认的项

| 项 | 说明 | 获取途径 |
|---|---|---|
| `WXPAY_MCH_SERIAL_NO` 商户 API 证书序列号 | 请求签名头 `serial_no` | 从 `apiclient_cert.pem` 读取（见 §四.2）或商户平台「账户中心-API安全-API证书」查看 |
| `WX_APPID` 小程序 AppID | 转账 payload 必填 `appid` | 商户平台绑定的小程序 AppID，须与 `WXPAY_ENABLED` 所用商户号完成**绑定**，否则报 `APPID_MCHID_NOT_MATCH` |
| 公网 HTTPS 回调地址 | `WXPAY_NOTIFY_URL`，微信回调推送 | 部署机公网域名或内网穿透（如 ngrok/cpolar），指向 `https://<domain>/api/pay/transfer/notify` |
| 商家转账产品权限 + 场景 ID | `transfer_scene_id`（如 1000 现金营销）及 `scene_report_infos.info_type` 枚举 | 商户平台「产品中心-商家转账」申请开通，`WXPAY_TRANSFER_SCENE_ID` 与报备信息必须严格匹配，否则发起即失败 |

#### 阶段 2：真实小额转账冒烟（核心）

**前置**：测试用户已在小程序登录建档、`real_name` 与微信实名一致、已绑卡；商户号与 AppID 已绑定；场景权限已开通。

1. 通过小程序「我的资金」发起一笔**小额提现（建议 0.30 ~ 5 元）**。
2. 观察后端日志 `auto_transfer_withdrawal`，记录：
   - 生成的 `out_bill_no`（形如 `WD0000000001A0`）；
   - 微信返回 `state`：预期 `ACCEPTED` / `PROCESSING` / `WAIT_USER_CONFIRM` 之一（用户确认模式通常先 `ACCEPTED` 或直接 `WAIT_USER_CONFIRM`）。
3. 查 DB：`SELECT id, out_bill_no, transfer_bill_no, transfer_status, status, retry_count FROM withdrawals ORDER BY id DESC LIMIT 3;` —— 预期 `status=pending`、`transfer_status=ACCEPTED`（或 PROCESSING/WAIT_USER_CONFIRM）。
4. 微信侧：测试用户打开微信「微信支付」转账消息，**点击「确认收款」**。
5. 回调到达后查 DB：`status=paid`、`transfer_status=SUCCESS`、`transfer_time` 已写、`paid_source=auto`、`pay_ref_no=out_bill_no`。
6. 小程序资金页：该笔显示「已到账」；余额已按申请金额扣减且未重复扣。

**验收**：
- 用户确认前：微信转账消息可见、状态「待收款确认」；
- 用户确认后：≤ 数秒内回调落库为 `paid`，余额无重复扣减；
- 到账金额 = 提现金额（无手续费差额，或与商户平台费率规则一致）。

#### 阶段 3：回调通知端点验证（签名/解密/幂等）

1. 确认 `POST /api/pay/transfer/notify` 公网可访问（`https://<domain>/api/pay/transfer/notify`）。
2. 构造非法报文（无签名 / 伪造 `Wechatpay-Signature` / 篡改 `Wechatpay-Serial`）→ 预期返回非 200（401/500），微信按重试策略重推，不影响既有记录。
3. 用微信真实回调（阶段 2 触发即可）核对日志：验签通过 → resource 解密 → `handle_transfer_event` 落库。
4. **幂等测试**：将同一笔回调报文用工具重放一次 → 预期二次处理不重复改状态、不重复入账（`status=paid` 已幂等短路）。
5. **陈旧回调**：伪造携带旧 `out_bill_no`（已被换单替换）的回调 → 预期日志 WARN 且被忽略。

**验收**：非法报文全部拒绝；重复/陈旧回调均幂等，DB 状态与余额不变。

#### 阶段 4：异常分支（不确认 / 失败）测试

| 场景 | 操作 | 预期结果 |
|---|---|---|
| **WAIT_USER_CONFIRM 展示** | 发起转账后不点确认，看小程序资金页 | 显示「待收款确认」+ 引导文案（去微信确认，非小程序内操作） |
| **CANCELLED 换单重试** | 等待微信超时取消（或不确认至取消）→ 第一次 CANCELLED 回调 | 自动生成新 `out_bill_no` 换单重试，`retry_count=1`，`status` 保持 `pending`，余额不退 |
| **CANCELLED 重试耗尽退余额** | 再次不确认至取消（第二次 CANCELLED） | `status=rejected`、`transfer_status=CANCELLED`、`balance_refunded=1`，**金额退回可提现余额**，小程序显示「已取消（余额已退回）」 |
| **防重复补发** | 对 `balance_refunded=1` 的单在管理后台点「失败补发」 | 返回 400「余额已退回，请重新申请」，不产生新转账 |
| **确定性 FAIL 转人工** | 构造确定性失败（如收款姓名与实名不符 `USER_NOT_EXIST`） | `classify_create_error` → FINAL_FAIL → 直接 `rejected`（不换单、不退余额），管理员可「失败补发」 |
| **QUERY_FIRST 防重** | 触发 `ALREADY_EXISTS`（同 out_bill_no 重复发起） | 先查单：查单 SUCCESS→置 paid；查单 FAIL→才换新号重试；结果未知→保持 pending，**绝不盲目换单** |

**验收**：所有分支均符合《业务说明.md》S6 状态机；任何分支都不出现「重复打款」「余额重复扣减/重复退回」。

#### 阶段 5：端到端验收（真实用户全流程）

1. 兼职完成作业 → 核验通过 → 佣金入账（`commissions.assignmentId` 幂等）。
2. 余额充足下提现 → 自动转账 → 用户微信确认收款 → 回调置 `paid`。
3. 小程序资金页全状态核对：转账中 → 待收款确认 → 已到账；失败/取消场景文案与余额正确。
4. 管理后台：提现列表「转账状态」列正确（SUCCESS 正常 / FAIL 红色 + fail_reason / 已退回标记）；台账/对账导出与 DB 一致。
5. 对账抽查：`SELECT * FROM withdrawals WHERE transfer_status='SUCCESS'` 的 `transfer_bill_no` 与商户平台转账单号一致。

### 六、回滚方案（联调中发现问题的处理）

1. 立即回滚：根目录 `.env` 置 `WXPAY_ENABLED=0` → `docker compose restart backend`。
2. 回滚后行为：提现自动打款关闭，退回原半自动流程（管理后台「确认到账」），无破坏性、不影响已发生转账的查询与补发。
3. 对账兜底：联调产生的每笔 `out_bill_no` 均可在商户平台「商家转账」查询，资金以商户平台为准。

### 七、风险与注意

- **防重复打款是最高优先级**：任何结果未知（`ALREADY_EXISTS`/网络异常等）都先查单，只有查单明确 `FAIL` 才换单重试。
- 用户确认模式：钱在用户未确认前冻结在转账单中，超时取消后钱退商户账户，系统此时才退余额——**不存在双花**。
- `scene_report_infos.info_type` 必须与商户平台已申请场景枚举严格一致，否则发起即 `PARAM_ERROR`（属 FINAL_FAIL，直接转人工，不会换单）。
- 测试尽量选真实小额，避免频繁测试造成 `FREQUENCY_LIMIT` 触发风控。
