# 左辅云创 · 兼职人员管理小程序 数据库结构说明

> 对应《兼职管理网站设计思路(1).docx》中"招募引流 → 注册准入 → 培训考试 → 任务派发 → 作业提交 → 质量检验 → 佣金结算 → 提现退出"全生命周期。
> 后端采用**前后端分离**架构下的 MySQL 关系型数据库。本文档中的"集合"即**关系表**，字段命名沿用原有集合字段语义并映射为下划线风格（如 `_openid`→`openid`、`claimedCount`→`claimed_count`）。
> 所有时间字段写入由后端使用数据库当前时间。用户维度数据均包含 `open_id`（微信 openid），用于权限与服务端归属判断。

---

## 一、集合总览

| 序号 | 集合名 | 用途 |
|------|--------|------|
| 1 | users | 用户（worker 兼职 / admin 管理员，三角色已并为 admin 兼财务） |
| 2 | balances | 用户佣金账户（可提现余额） |
| 3 | certifications | 能力认证（考试准入 + 能力等级 + 质量指标） |
| 4 | tasks | 任务（派发主体） |
| 5 | assignments | 领单 / 作业提交 |
| 6 | quality_checks | 外部核验结果 |
| 7 | commissions | 佣金流水（结算到日） |
| 8 | withdrawals | 提现记录（免审核） |
| 9 | violations | 违规 / 黑名单 |
| 10 | notices | 公告 / 流程 / 项目动态 / FAQ |

---

## 二、集合字段与索引详解

### 2.1 `users` 用户表

账号资格状态（status）与任务作业状态完全分离：本表 status 仅表示账号本身资格（正常/封禁），不包含"待审核"——因为"待审核"属于注册准入审批，独立收敛到 `approvalStatus` 字段；一人多任务的进度状态在 tasks / assignments 各自独立流转。

| 字段 | 类型 | 必填 | 说明 |
|------|------|:----:|------|
| _id | string | ✓ | 主键，系统自动 |
| _openid | string | ✓ | 微信 openid，登录凭证 |
| phone | string | ✓ | 手机号（实名） |
| realName | string | ✓ | 真实姓名（实名认证） |
| avatar | string | | 头像（云存储 URL） |
| nickname | string | | 昵称 |
| role | enum | ✓ | worker / admin |
| approvalStatus | enum | ✓ | pending(注册待审批) / approved(已通过) / rejected(已驳回)，仅表注册准入，与账号资格无关 |
| status | enum | ✓ | active(正常) / blocked(封禁)，账号资格状态 |
| bankInfo | object | | 提现账户：{ bankName, cardNo, cardHolder }，可不填（未绑定则无法提现） |
| inviterOpenid | string | | 邀请人 openid（可选，引流裂变） |
| createTime | date | ✓ | 注册时间 |

**索引**：`_openid`（唯一）、`phone`（唯一，防重复注册）、`approvalStatus`、`status`、`role`、复合 `(status, role)`

> 说明：新注册用户 `approvalStatus = pending`，管理员审批通过后置为 approved 方能接单；封禁仅体现在 `status = blocked`。

**关联**：1 — 1 `balances`；1 — N `certifications` / `assignments` / `quality_checks` / `commissions` / `withdrawals` / `violations`

---

### 2.2 `balances` 用户佣金账户表

仅冗余 `availableBalance`（可提现余额）作为唯一反规范化字段，支撑提现的原子扣减与防并发超提；**累计赚取 / 累计已提不落库**，需要时实时聚合 commissions / withdrawals 得出（方案 A，字段最少、无多字段一致性维护成本）。

| 字段 | 类型 | 说明 |
|------|------|------|
| _id | string | 主键 |
| _openid | string | 归属用户 |
| availableBalance | number | 可提现余额（当前可用，唯一冗余字段） |
| updateTime | date | 最近变动时间 |

**索引**：`_openid`（唯一）

**关联**：N — 1 `users`

**派生计算**（不落库，按需聚合）：
- `累计入账佣金 = sum(commissions.amount)`
- `累计已提金额 = sum(withdrawals.amount)`

**余额变化规则**：
- 外部核验通过（commission 入账）：`availableBalance += 金额`
- 提现：校验 `amount ≤ availableBalance`，成功后 `availableBalance -= 金额`
- 以上必须通过事务 / 原子递增保证并发安全

---

### 2.3 `certifications` 能力认证表

通过 `taskId + annotType` 唯一定位"某个任务 × 某类标注"的能力认证，与具体任务建立强关联。

| 字段 | 类型 | 说明 |
|------|------|------|
| _id | string | 主键 |
| _openid | string | 归属用户 |
| taskId | string | 关联的任务（认证绑定到具体任务） |
| taskName | string | 冗余任务名（便于展示） |
| annotType | enum | 标注类型：shadow(阴影) / light_source(光源) / reflection(反射) / exposure(曝光) / filter(特效滤镜) |
| level | enum | 能力等级：junior(初级) / middle(中级) / senior(高级) |
| examPassed | bool | 是否已通过该任务该类型考试（人工准入判定） |
| passRate | number | 该任务该类型的质检通过率（质量指标） |
| reviewedBy | string | 评审管理员 id（人工准入判定留痕，admin 写入 examPassed/level 时记录） |
| reviewTime | date | 评审时间（admin 评定通过/驳回的时间） |
| updateTime | date | 最近评定时间 |

**索引**：复合 `(_openid, taskId, annotType)`（唯一）、`taskId`

**关联**：N — 1 `users`；N — 1 `tasks`

---

### 2.4 `tasks` 任务表

| 字段 | 类型 | 说明 |
|------|------|------|
| _id | string | 主键 |
| title | string | 任务标题 |
| annotType | enum | 标注类型（同 certifications） |
| quantity | number | 单人任务量（每人领取本任务的作业数量） |
| claimedCount | number | 已领取人数（展示用；领取人达到总人数后停止领取） |
| totalPeople | number | 总人数（任务最大领取人数，必填，控制任务规模） |
| unitPrice | number | 单价（**单个作业**的佣金；每通过一个作业按此金额入账，非 quantity×unitPrice） |
| difficulty | enum | 难度：junior / middle / senior |
| requireLevel | enum | 领取所需最低能力等级 |
| deadline | date | 截止时间 |
| status | enum | open(可领取) / inProgress(进行中) / closed(已关闭)，**任务自身状态** |
| ownerId | string | 创建该任务的管理员 id |
| forbiddenItems | array | 禁用项说明（如私自改原图、编辑抖动伪影） |
| sampleUrl | string | 任务样例（可选，任务详情展示） |
| createTime | date | 创建时间 |

**索引**：`status`、`annotType`、`deadline`、复合 `(status, annotType)`

**关联**：1 — N `assignments`；1 — N `certifications`；1 — N `commissions`；1 — N `quality_checks`

---

### 2.5 `assignments` 领单 / 作业表

**一个用户可领取多个任务**，每领取一个任务产生一条 assignments 记录，独立流转。本系统不存储任务素材图（原图/编辑图）——用户在**外部专门任务系统**完成作业并提交；管理员审核时到外部系统核验通过与否，**仅将结果回写本系统**。

| 字段 | 类型 | 说明 |
|------|------|------|
| _id | string | 主键 |
| _openid | string | 领取人 |
| taskId | string | 所属任务（一个任务一个作业） |
| taskName | string | 冗余任务名 |
| status | enum | claimed(已领取) / submitted(已提交) / passed(已通过) / rejected(未通过) |
| zhInstruction | string | 中文指令 |
| enInstruction | string | 英文指令 |
| submitTime | date | 提交时间 |
| checkedBy | string | 审核管理员 id（在外部系统核验后回写） |
| auditTime | date | 审核通过时间（status → passed 的时间） |
| finishTime | date | 最终完成时间 |

**索引**：`_openid`、`taskId`、`status`、`checkedBy`（管理员待核验列表按人查）、复合唯一 `(_openid, taskId)`（一人一任务仅一条）、复合 `(_openid, status)`、复合 `(taskId, status)`

**关联**：N — 1 `users`；N — 1 `tasks`；N — 1 `commissions`（status = passed 时入账）

---

### 2.6 `quality_checks` 外部核验结果表

本系统不执行质检，质检判定在**外部专门任务系统**完成。管理员在外部核验后，将**最终结果（通过/未通过）**记录到此表用于留痕与追溯（与 assignments.status 联动，作为佣金入账的依据记录）。

| 字段 | 类型 | 说明 |
|------|------|------|
| _id | string | 主键 |
| assignmentId | string | 关联作业 |
| _openid | string | 作业人（冗余，便于按人统计） |
| taskId | string | 关联任务 |
| checkedBy | string | 核验管理员 id |
| result | enum | pass / reject（外部系统核验结果回写） |
| externalRefNo | string | 外部系统核验单号（可选，用于回查外部系统） |
| remark | string | 备注（如核验意见） |
| checkTime | date | 核验/回写时间 |

**索引**：`assignmentId`（唯一）、`_openid`、`taskId`、`result`、`externalRefNo`（外部单号回查频繁时用）

**关联**：N — 1 `assignments`；N — 1 `users`；N — 1 `tasks`

> 说明：外部质检细节（打分、具体打回原因、复检）留存于外部系统，本表仅记录最终判定结果。

### 2.7 `commissions` 佣金流水表

结算周期记录到"日"。质检通过即入账，进入用户可提现余额。

| 字段 | 类型 | 说明 |
|------|------|------|
| _id | string | 主键 |
| _openid | string | 归属人 |
| taskId | string | 来源任务 |
| assignmentId | string | 来源作业（按任务明细可追溯） |
| amount | number | 佣金金额（= 来源任务的单价 unitPrice） |
| settleDate | date | 入账日期（记录到日） |
| createTime | date | 创建时间 |

**索引**：`_openid`、`settleDate`、复合 `(_openid, settleDate)`、`taskId`、`assignmentId`（唯一，防重复入账）、复合 `(settleDate, _openid)`（对账报表按日聚合）

**关联**：N — 1 `users`；N — 1 `tasks`；N — 1 `assignments`

---

### 2.8 `withdrawals` 提现表（免审核）

提现不经过管理人员二次审核，仅校验可用余额是否足够。

| 字段 | 类型 | 说明 |
|------|------|------|
| _id | string | 主键 |
| _openid | string | 申请人 |
| amount | number | 提现金额 |
| bankAccount | object | 收款账户快照：{ bankName, cardNo, cardHolder } |
| status | enum | pending(提现中) / paid(已到账) / rejected(显余额不足被拒) |
| payRefNo | string | 微信支付/商户单号（到账回写时记录，用于对账回查，可选） |
| paidSource | enum | auto(自动回调) / manual(半自动确认)，区分到账回写路径 |
| applyTime | date | 申请时间 |
| paidTime | date | 到账时间 |

**索引**：`_openid`、`status`、复合 `(_openid, status)`

**关联**：N — 1 `users`；1 — N 与 `balances` 配合（余额校验 + 扣减）

## 三、关联关系总览（ER 关系）

```
users 1 ────── 1 balances
users 1 ────── N certifications
users 1 ────── N assignments ──── N 1 tasks
users 1 ────── N quality_checks ── N 1 assignments
users 1 ────── N commissions ───── N 1 assignments / tasks
users 1 ────── N withdrawals（提现扣减 balances）
users 1 ────── N violations
```

- `users` 为全系统主体，几乎所有业务集合都通过 `_openid` 关联到用户。
- `certifications` 与 `tasks` 通过 `taskId` + `annotType` 建立"任务级能力认证"关联。
- `quality_checks` → `assignments`：一次作业可对应一条外部核验结果记录（留痕）。
- `commissions` 由 `assignments.status == passed` 触发产生，同步写入用户佣金账户（balances）。
- 任务自身状态（tasks.status）与作业进度状态（assignments.status）完全分离，支撑一人多任务。

## 四、权限设计建议

> 前后端分离架构下，前端**不直连数据库**，无任何数据访问权限；全部数据读写经由后端 API，权限在后端鉴权层统一强制（详见《技术机制预研.md》第四章）。

- 默认：业务数据仅操作本人记录（后端按 `openid` 过滤）
- `tasks`、`notices`：所有登录用户可读，仅 `admin` 可写
- `balances`：仅本人可读；增减仅由后端结算逻辑在事务内修改
- `quality_checks`、`commissions`、`withdrawals`：读仅本人/admin；写仅由后端结算/回写逻辑触发，避免前端直接改余额
