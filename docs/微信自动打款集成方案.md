# 微信支付「商家转账到零钱」自动打款集成方案

> 文档版本：2026-09-03 ｜ 依据微信官方文档 2025.03.21《商家转账用户确认模式-发起转账》接口
> 关联：后端提现流程（backend/app/api/wallet.py）、Withdrawal 模型（backend/app/models.py）

## Context（背景与目标）

本系统（Flask 兼职管理 + 微信小程序）目前提现流程为：兼职申请提现 → 扣余额写 `withdrawals(status=pending)` → 财务在管理后台手动确认到账（半自动）。

目标：接入微信官方「商家转账到零钱」APIv3，实现**提现申请即全自动打款**，并已确认三项决策：

1. **触发方式**：兼职提交提现后，后端同步调用微信转账 API 自动打款，无需管理员干预。
2. **失败处理**：转账最终失败(FAIL)时**自动换单重试一次**（严格遵循官方防重铁律：遇 `ALREADY_EXISTS`/`FREQUENCY_LIMIT_*`/`SYSTEM_ERROR` 等必须先查单，查单明确 FAIL 才允许生成新 `out_bill_no` 重试；绝不立即换单，防止重复转账资金风险）。重试仍失败 → 状态置 rejected、记录 fail_reason、**余额不自动退回**，由管理员「补发」处理。
3. **小程序端**：同步更新「我的资金 / 提现记录」状态展示（转账中 / 待收款确认 / 已到账 / 已拒绝+原因）。

技术约束：Python 实现，不引入第三方微信支付 SDK，复用现有 `requests` + `cryptography`（43.0.3，已支持 RSA-OAEP(SHA-1)、AES-256-GCM、SHA256 签名）。

## 架构分层

- **`backend/app/wxpay/` 纯协议层**：不 import models/db，只负责 APIv3 签名、加解密、HTTP 请求、payload 构建、错误码分类。可脱离 Flask/DB 验证。
- **`backend/app/api/wallet.py` 业务编排层**：持有 Withdrawal 状态机，负责「何时发起、查单后是否换单重试、状态落库」等业务策略（复用现有 `login_required`/`require_role`/`_withdrawal_view` 风格）。

理由：防重/换单是**业务策略**（重试上限、余额不退、转人工），错误码含义是**协议事实**，两层职责清晰、可独立验证。

## 关键实现细节

### 1. wxpay 协议层

- **请求签名**：`message = f"{method}\n{url_path}\n{timestamp}\n{nonce}\n{body}\n"`，商户 API 私钥 SHA256withRSA 签名后 base64；`Authorization: WECHATPAY2-SHA256-RSA2048 mchid="..",nonce_str="..",signature="..",timestamp="..",serial_no=".."`。
- **敏感字段**：`user_name` 用微信支付公钥 RSA-OAEP(**SHA-1**) 加密 + base64；请求头带 `Wechatpay-Serial = 微信支付公钥ID`。
- **回调验签**：`message = f"{timestamp}\n{nonce}\n{body}\n"`，微信支付公钥验 `Wechatpay-Signature`；比对 `Wechatpay-Serial` 与配置的公钥 ID 防公钥轮换攻击。
- **回调解密**：`resource{nonce, ciphertext, associated_data}` 用 32 位 APIv3 key AES-256-GCM 解密。
- **防重决策表** `classify_create_error(code)`：
  - `QUERY_FIRST`（结果未知，先查单）：`ALREADY_EXISTS` / `SYSTEM_ERROR` / `FREQUENCY_LIMIT_EXCEED` / `FREQUENCY_LIMIT` / `RATELIMIT_EXCEEDED` / 网络异常(Timeout/ConnectionError)。
  - `FINAL_FAIL`（确定性失败，换单必败，直接转人工）：`PARAM_ERROR` / `INVALID_REQUEST` / `NO_AUTH` / `SIGN_ERROR` / `NOT_ENOUGH` 等。
  - **只有 `QUERY_FIRST` 且查单结果明确 `FAIL` 才允许换单重试**，否则绝不生成新 `out_bill_no`。

### 2. 数据模型与迁移

Withdrawal 新增列（与 003 一致）：
| 列 | 类型 | 说明 |
|---|---|---|

`003_wxpay_withdrawal.sql`：`ALTER TABLE withdrawals ADD COLUMN ...` + `ADD UNIQUE KEY uk_wd_out_bill_no (out_bill_no)` + `ADD KEY idx_wd_transfer_status (transfer_status)`。

- 存量 mysql_data 卷不会重放迁移（项目已知教训），需手动执行（PowerShell）：

### 3. 提现申请自动打款流程（wallet.py）

```
apply_withdrawal:
  1. 校验 amount>0、已绑卡、余额充足（不变）
  2. 事务内扣 available_balance + 写 Withdrawal(status=pending)；commit
     （HTTP 调用绝不放事务内，避免持锁；先落库拿 id）
  3. 提交后同步调用 auto_transfer_withdrawal(record)
  4. 返回 {"code":0, "data":_withdrawal_view(record)}

auto_transfer_withdrawal(w):
  client = wxpay.get_client(current_app)
  if client is None: return  # 未启用 → 保持 pending，沿用 manual 兜底
  while w.retry_count <= WXPAY_RETRY_MAX:
    out_bill_no = _gen_out_bill_no(w.id, w.retry_count)   # f"WD{id}A{attempt}" 纯数字字母
    try:
      resp = client.create_transfer_bill(build_transfer_payload(...))
    except WxpayError as e:
      if classify_create_error(e.code) == 'QUERY_FIRST':
        q = client.query_transfer_bill(out_bill_no)       # 先查单，绝不直接换单
        state = normalize_query(q)
        SUCCESS → _mark_paid; FAIL → retry_count<MAX 则重试 else _mark_rejected; 其余 → _keep_pending
      else:  # FINAL_FAIL
        _mark_rejected(w, e)                               # 换单必败，转人工，余额不退
    except (Timeout, ConnectionError):
      _keep_pending(w)                                     # 结果未知，防重复打款
    state = normalize_create(resp)  # 2xx
    SUCCESS → _mark_paid; FAIL → 重试/转人工; 其余 → _keep_pending
```

私有辅助（均在 wallet.py）：
- `_gen_out_bill_no(id, attempt)`：纯数字字母、商户内唯一、随 attempt 递增保证每次换单都是新号。
- `_mark_paid`：`status=paid, paid_source=auto, pay_ref_no=out_bill_no, transfer_bill_no, transfer_status=SUCCESS, transfer_time=paid_time=now`。
- `_keep_pending`：只更新 `out_bill_no/transfer_bill_no/transfer_status`，status 保持 pending（前端显示「转账中」）。
- `_mark_rejected`：`status=rejected, transfer_status=FAIL, fail_reason=...`；**不回滚余额**（管理员补发处理）。

`handle_transfer_event(out_bill_no, event)`（notify 共用同一套收口，幂等）：
- 按 `out_bill_no` 查记录；查不到或 `event.out_bill_no != w.out_bill_no`（陈旧回调）→ 忽略。
- SUCCESS → `_mark_paid`；FAIL → 未达上限则换单重试一次，否则 `_mark_rejected`；其余 → `_keep_pending`。

### 4. 回调 notify 端点

`POST /api/pay/transfer/notify`（无登录鉴权，微信签名保护）：
1. `request.get_data()` 原文 → `client.verify_notify(headers, raw_body)`，失败返回 `{"code":"FAIL","message":"验签失败"}` + 非 200（微信会重试）。
2. 解密 resource → 事件 dict（out_bill_no / transfer_bill_no / state / fail_reason / success_time）。
3. 幂等 + 陈旧忽略（见 `handle_transfer_event`）；查不到记录 → WARN 日志 + 返回 200 SUCCESS（停止微信无限重推）。
4. 返回 `200 {"code":"SUCCESS"}`。

### 5. 管理后台

- `POST /api/wallet/withdrawals/<id>/retry`（`require_role("admin")`）「失败补发」：仅允许 rejected/FAIL（或 pending 但无 out_bill_no 的历史残留单）；**若已有 out_bill_no 先查单**，若旧单已 SUCCESS 则直接置 paid（防重复打款），否则清空转账字段、`retry_count=0`，重新调 `auto_transfer_withdrawal`；不重复扣余额。
- 既有 `POST .../confirm` 保留（manual 兜底）。
- `app.js`：提现列表新增「转账状态」列（FAIL 红色 + fail_reason）；pending 行保留「确认到账」；rejected 行加「失败补发」按钮 `doRetryPaid(id)`。

### 6. 小程序 wallet 页

- `wallet.js`：`WD_STATUS = { pending: '转账中', paid: '已到账', rejected: '已拒绝' }`；`transfer_status==='WAIT_USER_CONFIRM'` 时显示「待收款确认」；透传 `transfer_status / fail_reason`。
- `wallet.wxml`：rejected 项补 `失败原因：{{item.fail_reason}}`；`onWithdraw` 成功提示改「提现已受理，转账中」。

## 验证 / 自测（无真实商户凭据）

1. **`flask wxpay-selfcheck`**（新增 CLI，零依赖零凭据）：内存生成临时 RSA 密钥对，断言签名回环、OAEP-SHA1 加解密一致、AES-GCM 回解、`classify_create_error` 决策表（ALREADY_EXISTS→QUERY_FIRST、PARAM_ERROR→FINAL_FAIL 等）。
2. **`WXPAY_MOCK=1` 全链路冒烟**：mock 客户端 create 返回 ACCEPTED / query 返回 SUCCESS，本地 MySQL 走完「扣余额→写记录→发起→状态回写」；curl POST `/api/pay/transfer/notify`（mock 跳过验签）触发 SUCCESS/FAIL，断言 DB 状态迁移 + 陈旧回调（伪造旧 out_bill_no）被忽略。
3. **防重单测（核心安全项）**：构造 `ALREADY_EXISTS` → 断言先查单、查单 FAIL 才换 `out_bill_no`（retry_count 0→1）、查单 SUCCESS 直接置 paid 不换单；确定性错误直接 rejected 不换单。
4. **真实凭据阶段**：`WXPAY_ENABLED=1` + 真实证书，内网穿透暴露 notify URL，发起小额真实转账，核对回调落库与小程序状态展示。

## 风险与注意

- 同步调用延迟：HTTP 调用不放 DB 事务内；`requests.timeout=10`；失败落 `_keep_pending` 转人工对账，绝不盲目换单（防重复打款最高优先级）。
- 存量 `pending` 无 `out_bill_no` 的历史记录：`retry` 接口可对其补发起。
- 老数据卷不回放迁移：003 必须手动执行，且 `models.py` 同步加列，防止 schema 脱节。
- `WXPAY_ENABLED=0` 时行为完全回退到现有半自动流程，无破坏性。
