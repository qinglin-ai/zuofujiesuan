## 二、状态机定义（冻结）

### 2.1 任务状态（tasks.status）—— 任务自身生命周期

```
open ──满员/开工──▶ inProgress
open/inProgress ──到期或手动──▶ closed（终态）
closed：未领取名额失效，已领取作业继续按核验流程结算
```

| 状态 | 含义 | 触发 |
|------|------|------|
| open | 可领取 | 创建后初始态 |
| inProgress | 进行中（满员开工） | claimedCount 达 totalPeople |
| closed | 已关闭 | 到达 deadline 或 admin 手动关闭 |

### 2.2 作业状态（assignments.status）—— 单个作业进度（一人一任务一条）

```
claimed ──提交──▶ submitted ──核验──▶ passed（→ 触发结算）
                              └──▶ rejected（不结算）
```

| 状态 | 含义 | 触发 |
|------|------|------|
| claimed | 已领取 | 领取成功 |
| submitted | 已提交 | worker 在外界作业完成并提交 |
| passed | 已通过 | 外部核验通过回写 |
| rejected | 未通过 | 外部核验未通过回写 |

### 2.3 提现状态（withdrawals.status）

```
pending ──微信转账成功回调──▶ paid
pending ──转账终态失败/余额不足──▶ rejected
```

| 状态 | 含义 | 触发 |
|------|------|------|
| pending | 提现中（含「待收款确认/转账中」微信侧中间态） | 用户申请成功、余额扣减后 |
| paid | 已到账 | 微信转账 SUCCESS 回调 / admin 半自动确认对账 |
| rejected | 已拒绝 | 校验失败（余额不足等）或转账终态 FAIL（达重试上限） |

> 微信侧单据状态镜像 `transfer_status`（ACCEPTED / PROCESSING / WAIT_USER_CONFIRM / TRANSFERING / SUCCESS / FAIL / CANCELING / CANCELLED）同步落库，`status=pending` 期间可据此细分展示「待收款确认/转账中」。

### 2.4 用户状态（users 双字段分离）

- `approvalStatus`（注册准入）：pending → approved / rejected
- `status`（账号资格）：active / blocked

> 资格状态与作业进度完全分离，支撑一人多任务独立流转。

## 三、主链路逐步详解

### S1 创建（admin）
- 输入：任务名、任务描述、标注类型、quantity、unitPrice、难度、requireLevel、totalPeople、deadline、forbiddenItems、样例
- 落库：tasks(status=open, claimedCount=0)
- 异常：无（admin 权限校验）

### S2 领取（worker）
- 前置校验（缺一不可）：审批通过 `approvalStatus=approved`、账号正常 `status=active`、考试准入通过、能力等级满足 requireLevel、未领取过该任务、未满员 `claimedCount<totalPeople`
- **并发控制（⚠关键）**：云函数事务内读取 claimedCount → 判断未满员 → 原子 +1 → 插入 assignment
- 兜底：assignment 复合唯一索引 `(_openid, taskId)`
- 满员：同事务内将 tasks.status 置 inProgress
- 异常分支：见第四章

### S3 提交（worker，作业在外部系统）
- 外部系统完成作业 → 本系统 assignment 置 submitted，记 submitTime
- 异常：未领取不可提交（状态机校验）

### S4 外部核验回写（admin）
- admin 到外部系统核验 → 回写本系统 pass/reject
- 落库：assignment → passed/rejected + quality_checks（result、externalRefNo、remark、checkTime、checkedBy）
- **通过才触发结算**

### S5 结算（核验通过自动触发，⚠关键）
- 佣金金额 = 提交数量 × unitPrice；`commissions.assignmentId` 唯一索引保证幂等
- 事务：插佣金流水 + balances.availableBalance += 金额，任一失败回滚
- 记 assignment.finishTime

### S6 提现（worker）与回写
- 申请：校验 `amount ≤ availableBalance` 且已绑卡 → 事务内 balances -= amount + 写 withdrawals(pending)（HTTP 调用不放事务内）
- 到账（自动为主，T4-6）：提交后同步调用微信「商家转账到零钱」创建转账单；异步回调 SUCCESS → 置 paid；**防重铁律**——创建遇 `ALREADY_EXISTS`/`SYSTEM_ERROR`/`FREQUENCY_LIMIT_*`/网络异常等结果未知错误时**先查单**，仅当查单明确 FAIL 才生成新 `out_bill_no` 换单重试（上限 1 次），绝不盲目换单防重复打款
- 到账（半自动兜底）：未启用自动打款（`WXPAY_ENABLED=0`）或自动流程异常时，保留 pending，由财务「确认到账」置 paid
- 失败：校验不通过或转账终态 FAIL 达重试上限 → 置 rejected + 记录 fail_reason，**余额不自动退回**，由管理员「失败补发」重新打款
- 提现免 admin 二次审核；未绑定收款账户不可提现

### S7 关闭
- deadline 到达或 admin 手动关闭 → tasks.status=closed
- 未领取名额失效；已提交待核验作业继续走 S4~S5 结算

## 四、异常分支与约束（冻结）

| 编号 | 场景 | 处理 | 归属状态机 |
|------|------|------|-----------|
| E1 | 并发同时领取同一任务最后名额 | 事务条件自增，who claimedCount<totalPeople，仅一方成功，其余返回「任务已满员」 | S2 |
| E2 | 同一人重复领取同一任务 | 复合唯一索引 `(_openid, taskId)` 拒绝 | S2 |
| E3 | 未满员但已关闭的任务 | 无 S2 领取入口（closed 不可领） | S2/S7 |
| E4 | 核验重复回写 | 以 assignmentId 幂等（单条）+ quality_checks 唯一索引防重 | S4 |
| E5 | 结算重复触发 | commissions.assignmentId 唯一索引幂等 | S5 |
| E6 | 提现余额不足 | 校验失败 → withdrawals=rejected，不扣金额 | S6 |
| E7 | 提现到账回写失败 | 自动打款异常（网络/超时结果未知）→ 保留 pending 防重复打款，回调或查单兜底 / admin 半自动确认到账兜底 | S6 |
| E8 | 关闭后再被核验 | 已领取作业继续核验结算，不受 closed 影响 | S4/S7 |
| E9 | 考试未通过仍领取 | S2 前置校验拦截（examPassed=false） | S2 |
| E10 | 自动打款创建单遇 ALREADY_EXISTS 等结果未知错误 | **先查单**：查单 SUCCESS → 直接置 paid；明确 FAIL → 生成新 out_bill_no 换单重试（≤1 次）；其余状态 → 保持 pending 等回调；绝不盲目换单（防重复转账资金风险） | S6 |
| E11 | 微信回调幂等 / 陈旧回调 | 回调按 out_bill_no 定位；已终态忽略；`event.out_bill_no` 与当前 `out_bill_no` 不一致（已换单）的迟到回调忽略 | S6 |
