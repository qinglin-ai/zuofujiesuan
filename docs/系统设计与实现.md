## 一、系统架构与开发规划


> 本文档在《业务说明.md》《数据库结构说明.md》基础上，从**整体架构、开发周期、开发阶段**三个维度对系统进行规划，作为项目从设计到落地的总体路线图。
> 技术底座：**前后端分离**。前端为微信原生小程序（界面展示 + 用户交互）；后端为独立的云服务端（Python Flask + MySQL），以 REST API 对外提供服务。涉及资金与并发安全的逻辑必须由后端服务承载，并配合数据库事务 / 唯一索引兜底。

---

### 一、系统整体架构

#### 1.1 架构总览

系统采用**前后端分离**架构：前端小程序只负责界面展示与用户交互（数据经后端 API 获取/提交），全部核心业务逻辑、数据持久化与资金/并发安全收敛到后端云服务端。前端不直连数据库，无业务数据访问权限。

```
┌──────────────────────────────────────────────────────────────┐
│ 前端（小程序端，界面 + 交互）                                  │
│  ┌───────────────┐   ┌────────────────┐                     │
│  │ 兼职人员端小程序 │   │ 管理后台(H5/小程序端)                 │
│  │ 浏览/领取/提交/  │   │ 审批/建单/核验/对账/处罚               │
│  │ 查余额/提现     │   │               │                     │
│  └───────┬───────┘   └───────┬────────┘                     │
│          │   wx.request (HTTPS + Token 鉴权)                 │
├──────────┼──────────────────────────────────────────────────┤
│  接入层 / 反向代理（Nginx，HTTPS / 负载 / 静态托管）            │
├──────────┼──────────────────────────────────────────────────┤
│ 后端服务（云服务端：Python Flask，承载全部核心业务逻辑）        │
│  认证鉴权(JWT) │ 业务API │ 并发控制 │ 幂等处理 │ 事务管理 │对账 │
│  注册审批  /  能力认证  /  任务派发  /  作业提交  /  佣金结算 / 提现 │
│  （SQLAlchemy ORM，事务由连接会话管理）                        │
├──────────┼──────────────────────────────────────────────────┤
│ 数据层（MySQL）                                               │
│  表：users/balances/certifications/tasks/assignments/        │
│       quality_checks/commissions/withdrawals/violations/     │
│       notices  （详见《数据库结构说明.md》，集合已映射为关系表）│
├──────────┼──────────────────────────────────────────────────┤
│ 外部系统（专门任务系统 / 微信支付）                             │
│  作业提交与质检判定在外部系统；本系统仅回写结果与结算资金         │
└──────────┴──────────────────────────────────────────────────┘
```

#### 1.2 分端职责划分

| 端 | 职责 | 说明 |
|----|------|------|
| 兼职人员端（小程序） | 浏览/领取任务、提交作业、查看数据与佣金、申请提现、参加考试 | 仅负责界面与交互；数据均由后端 API 返回 |
| 管理后台（前端） | 注册审批、任务创建/分配、外部核验回写、能力评级、台账对账导出、违规处罚 | admin 专属入口，操作指令经后端 API，后端校验角色 |
| 后端服务（Flask） | 认证鉴权、全部核心业务逻辑、事务/幂等/并发控制 | 涉及资金与并发的逻辑唯一承载方；对前端封闭数据库 |
| MySQL | 业务数据持久化（关系型） | 唯一约束/索引兜底并发与幂等 |
| 前端不直连 | 无数据库访问能力 | 数据只能经后端 API 读写，杜绝客户端越权 |
| 外部任务系统 | 作业提交、质检判定 | 本系统的数据/资金依据来源 |

#### 1.3 关键架构约束（安全 / 资金 / 并发）

1. **资金安全**：佣金入账、提现扣减必须由后端在**同一事务**内完成，"流水与余额一致"。
2. **并发防超领**：`claimedCount` 由后端用**原子条件 UPDATE**（`< totalPeople` 时 +1）+ assignments 复合唯一索引 `(_openid, taskId)` 双保险。
3. **结算幂等**：`commissions.assignment_id` 唯一索引，防止重复结算。
4. **权限隔离（前后端分离）**：前端无数据库写权限；后端通过鉴权层校验每个请求的身份与角色（`role == admin` 才允许敏感操作），并对越权请求返回 403（详见本文第二部分《技术机制预研》）。
5. **数据与系统解耦**：本系统不存作业素材图，仅回写外部核验结果（`quality_checks.external_ref_no` 用于跨系统追溯）。
6. **防重复打款（T4-6 自动打款）**：微信转账创建单遇结果未知错误（`ALREADY_EXISTS`/`SYSTEM_ERROR`/`FREQUENCY_LIMIT_*`/网络异常）时**必须先查单**、明确 FAIL 才换 `out_bill_no` 重试（≤1 次），绝不盲目换单，杜绝重复转账资金风险；回调按 `out_bill_no` 幂等收口、陈旧回调忽略。

## 二、关键技术机制预研（T1-4 交付物）


> 阶段一 T1-4「关键机制预研」产出，针对资金与并发安全落地到**前后端分离**（Python Flask + MySQL）的具体实现方案。覆盖：**事务、原子更新、唯一约束、鉴权与权限校验**四类机制，供阶段二基础搭建与阶段三/四开发直接采用。

---

### 一、事务（Database Transaction）

#### 目标
保证"多表单写入原子性"：任一失败整体回滚，避免残缺数据与资金不一致。

#### 适用场景
| 场景 | 涉及表 | 说明 |
|------|----------|------|
| 任务领取 | tasks(claimed_count+1) + assignments(插入) | 并发防超领核心 |
| 佣金入账 | commissions(插入) + balances(available_balance 加) + assignments(finish_time) | 流水与余额一致 |
| 提现申请 | balances(available_balance 减) + withdrawals(插入) | 成功率/扣款原子 |

#### MySQL/SQLAlchemy 实现要点
- 使用 SQLAlchemy **会话事务**：同一视图函数内所有 ORM 读写共用一个 `Session`（`sessionmaker(bind=engine)`）。
- 顺序：开启事务（`session.begin()`）→ 事务内查询校验 → 事务内写（`session.add/.commit`）→ `session.commit()`；任一步抛错则 `session.rollback()`。
- **事务边界**：`@transaction` 装饰器统一管理 commit/rollback，避免散落 try/except。
- 注意：领取场景可用更轻量的**原子条件 UPDATE**（见 §二），减少锁与事务冲突。
- 错误处理：捕获后返回业务错误（如"任务已满员"），避免通用 500。

---

### 二、原子条件更新（Atomic Conditional UPDATE）

#### 目标
避免"读-改-写"竞态，使并发场景下不超领、不超提。

#### 适用场景
- 任务领取：`claimed_count` 原子 +1（仅当未满员）
- 余额变化：`balances.available_balance` 原子增减

#### MySQL/SQLAlchemy 实现要点
- 使用 `UPDATE ... SET x = x + 1 WHERE 条件` 单条原子语句，而非先读后写。
- 领取代码范式（后端调用）：
```python
# 原子条件自增：仅未满员且 open 状态才 +1，返回值受影响行数为 1 表示成功占用名额
stmt = (
    update(Task)
    .where(Task.id == task_id,
           Task.claimed_count < Task.total_people,   # 条件更新：未满员才 +1
           Task.status == 'open')
    .values(claimed_count=Task.claimed_count + 1)     # 原子自增
)
res = db.session.execute(stmt)
db.session.commit()
# res.rowcount == 1 表示成功占用名额，否则视为满员/已关闭
```
- 余额加减同理，用条件 UPDATE 或事务内更新，保证并发下数值正确。
- 说明：`x = x + 1` 为原子操作，消除"两请求读到同一值后各自 +1 写回"的覆盖问题。

### 三、唯一约束与索引（UNIQUE Index）

#### 目标
数据库层兜底，即使业务逻辑或事务边界漏网，也拒绝并发重复写入，形成"双保险"。

#### 落地清单
| 唯一约束 | 表 | 防什么 |
|----------|------|--------|
| 复合 `(openid, task_id)` | assignments | 同一人重复领取同一任务（并发超领 / 重复领取） |
| `assignment_id` | commissions | 同一作业重复结算（幂等） |
| `assignment_id` | quality_checks | 同一作业重复核验回写 |
| `phone` | users | 手机号重复注册 |
| `openid` | balances / users | 一人一账户 |

#### 实现要点
- 在 MySQL 建表/迁移脚本 `.sql` 中为对应表创建 UNIQUE 键（见《数据库结构说明.md》各表索引）。
- 唯一约束冲突会抛 `IntegrityError`，后端需捕获并转为友好业务提示（如"您已领取该任务"）。
- 依赖**先查后写**之前先保证索引已建，否则并发下可能出现短暂重复。

---

### 四、鉴权与权限校验（Authentication & Permission）

#### 目标
杜绝前端越权访问，敏感数据仅允许合法身份与角色访问。

#### 设计（对应《数据库结构说明.md》第四章）
| 表 | 读 | 写 |
|------|-----|-----|
| 默认业务表 | 本人可读（openid 匹配） | 本人可写（openid 匹配） |
| tasks / notices | 所有登录用户可读 | 仅 admin 可写 |
| balances | 仅本人可读 | 禁止前端写，仅后端结算逻辑修改 |
| commissions / quality_checks / withdrawals | 本人或 admin | 仅后端结算/回写逻辑写入 |
| violations | admin | admin |

#### 实现要点
- **统一鉴权中间件**：JWT 签发（登录成功后下发），后续请求带 `Authorization: Bearer <token>`，中间件解码后注入当前 `openid` 与 `role`。
- **角色校验装饰器**：`@require_role('admin')` 作用于敏感接口（建单、审批、核验回写、违规处罚、对账导出），非 admin 返回 403。
- 每个写操作在后端内校验 `openid` 归属与角色，前端不直连数据库、无数据写能力，从源头杜绝越权。
- admin 识别：`users.role` 持久化，权限校验读取 token 中缓存的 role 或回表核验。
- 补充：金额类字段（available_balance 等）不仅靠权限，还需结合事务/原子更新，防止非法请求构造。

### 五、组合策略小结

| 场景 | 策略组合 |
|------|----------|
| 防并发超领 | 原子条件 UPDATE（`x+1` + `< total_people`）为主 + 唯一约束兜底 + 事务护栏 |
| 防重复结算 | 唯一约束（assignment_id）为主 + 先查后写幂等 + 事务护栏 |
| 资金一致 | 事务（流水+余额同写）+ 原子增减 + 后端权限隔离（前端无 DB 写权限） |
| 提现闭环 | 事务扣减 + 状态机约束 + 回写唯一化（见业务流程图解） |

> 预研结论：四项机制均为 Flask/SQLAlchemy/MySQL 原生能力，无额外中间件依赖；建议在阶段二 T2-4 基建中预建唯一约束/索引迁移脚本与鉴权基线，阶段三/四直接套用本方案。

#### 2.5 用户页（我的）
```
┌──────────────────────────┐
│ 我的账号                  │
│  [头像] 昵称  [设置头像]  审批状态徽标 │ ← chooseAvatar 上传至 POST /api/users/avatar
│  · 已绑定（只读）：手机号(脱敏) 真实姓名(脱敏) 昵称 │
│  · 未绑定 / 已驳回：手机号+真实姓名+昵称 输入 + 协议勾选 + [提交绑定] │
├──────────────────────────┤
│ 收款银行卡                │
│  · 已绑定：开户行 ···尾号（持卡人脱敏） [更换银行卡] │
│  · 未绑定：开户行/卡号(16~19 位数字)/持卡人 + 协议勾选 + [绑定银行卡] │
├──────────────────────────┤
│ 能力认证 / 用户服务协议 / 隐私政策 / 退出登录 │
└──────────────────────────┘
```
- 手机号与真实姓名由用户手动输入（非微信授权获取），提交后进入「待审批」；`approval_status=approved` 后前端隐藏表单、后端 `POST /api/users/register` 直接返回 400，防止越权改实名。
- 实名信息与收款银行卡均须先勾选《用户服务协议》《隐私政策》方可提交（合规：先授权后收集）。
- **脱敏口径**统一在 `miniprogram/utils/mask.js`：手机号 `187****4688`、真实姓名 `刘*余`（保留首末字，单字不遮蔽）；收款账户一律展示为「开户行 ···尾号（持卡人脱敏）」，页面不出现完整卡号与完整姓名。
- **银行卡号校验** `^\d{16,19}$`（国内借记卡多为 16/17/19 位、信用卡 16 位），由 `POST /api/wallet/bank` 负责强校验，小程序提交前同规则先行提示。

### 四、状态-界面映射（一致性约束）

| 状态 | 兼职端呈现 | 管理端可操作 |
|------|-----------|-------------|
| tasks.status=open | 可领取（详情页显示「领取」） | 可关闭 |
| tasks.status=closed | 置灰、不可领 | - |
| assignments=claimed | 待作业（去外部系统） | - |
| assignments=submitted | 待核验文案 | 核验回写（通过/未过） |
| assignments=passed | 显示佣金 + 审核人/时间 | - |
| assignments=rejected | 未通过，不显示佣金 | - |
| withdrawals=pending | 提现中 | 确认到账（半自动） |
| withdrawals=paid | 已到账（到账时间） | - |
| withdrawals=rejected | 被拒（原因：余额不足） | - |
| approvalStatus=pending | 提示等待审批 | 通过/驳回 |
| status=blocked | 禁止操作 | 封禁/解封 |

### 五、设计与实现说明

1. 本文档为**线框级原型**，实现阶段由 UI 产出高保真并落码。
2. 交互与状态机严格对应《业务说明.md》与《数据库结构说明.md》，避免页面状态与业务状态错位。
3. 资金相关按钮（领取、提现）一律经云函数校验，前端仅做展示与触发，不做业务判断主控。
4. 管理后台为 H5，采用表格密集布局；兼职端为小程序，采用卡片/tab 布局。
